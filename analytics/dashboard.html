Adoption analytics

We collect high-level usage metrics to understand how the driver is used and help improve it. Your SQL statements, query parameters, query results and database contents are not collected.

Distinct active installation IDs: each ID counts once if it has a query attempt received in the last 7 days. These are not unique machines or people. New clients save a generated ID in the local user configuration directory and reuse it across handles and restarts. An application-supplied ID takes precedence. Read-only storage falls back to a temporary ID, which can inflate this count. Older clients used a new ID per handle. Containers can receive new installation IDs; automatic deployment associations below track supported platform workloads across replacements.

Automatically associated deployments

No UUID configuration or mounted ID file is required. Deployment IDs are assigned automatically. Matching platform workload hashes associate replacement containers; matching installation IDs preserve continuity when networks change. Runtime instances are counted separately. Identifier matches are self-reported, not verified customer identities. Older reports without an association are excluded here.

Probable network associations

Shared public IP or reverse DNS can suggest related containers, but also occurs with NATs, VPNs and shared infrastructure. These suggestions never merge deployment IDs or reduce the associated-deployment count.

Recent query workloads

See work for each sampled execution, rather than adding rows across unrelated queries. Query text, values, table names and parameters are not collected. An execution ID identifies one call; a script or parameter batch is one call.

Index documents observed: point-in-time index sizes from readiness checks already made by the query; an index may cover more than one logical table. Driver row candidates: rows fetched for driver-side evaluation, including repeated scans. Pushdown rows represented: source rows represented by aggregate tuples, including retries. These are different measures, not Redis internal rows scanned. Not applicable means the counter does not apply to this operation. Unavailable means the driver did not report it; see Measurement notes or hover over the cell. Unavailable never means zero, and the reason cannot always be determined from a report. No extra scans are run for analytics. Returned rows count batches delivered to the caller; elapsed time includes fetching.

Reporting hosts and networks

Hostnames are reported by clients and may be short or internal names. Public reverse DNS is a best-effort PTR lookup of the observed egress IP; NAT, VPNs and proxies can represent many machines. Neither identifies a verified company. Older reports cannot supply missing source data. Reload after a few seconds while DNS lookups finish.

Statement types and outcomes

One attempt = one ExecuteQuery/ExecuteUpdate call, including an entire script or parameter batch. Success requires result exhaustion. Latency includes application fetch time; histogram percentiles are upper bounds.

Download snapshots

Downloads measure distribution activity, not unique users. GitHub build assets may be fetched by packaging jobs. Channels are shown separately.

Week-4 retention: installations with a successful execution 28–35 days after their first observed successful execution; only cohorts with the full 35-day window are eligible. Installation IDs must remain stable. Missing telemetry, blocked networks and opt-out users are outside this view.
